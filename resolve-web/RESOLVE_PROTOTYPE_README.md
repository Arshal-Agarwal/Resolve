# Resolve Prototype Frontend

## Overview

This directory contains the Resolve frontend prototype, built on React 19 and TanStack Start. It extends the existing Lovable/TanStack application while keeping all prototype data in local browser state.

The application is backend-independent. It does not make service API requests and does not require Authentication, Organization, RBAC, User & Team, Document, Audit, PostgreSQL, Redis or Kafka services.

## Shared mock state

All prototype data is stored in `src/lib/resolve-store.tsx` and persisted in localStorage under `resolve.store.v3`.

The central store contains:

- organizations and selected tenant
- users and teams
- roles and permissions
- user-role assignments
- workflows and stages
- cases and case state
- tasks and task dependencies
- approvals
- comments
- documents
- notifications
- audit events
- service-status mock data
- prototype toast and busy-action state

The store uses stable seed IDs and related entity references. It also exposes local operations for create, update, delete, assign, status change, completion, document upload and audit recording.

## Simulated operations

Mock mutations use a short simulated delay and display:

- saving/busy state
- success toast
- confirmation dialogs
- validation-disabled actions
- empty and filtered-empty states

The prototype does not use random dashboard metrics. Stable demo values are restored from seed state and update as related entities change.

## Persistence and reset

The application loads `resolve.store.v3` from browser localStorage. Invalid or missing stored data falls back to demo seed data.

Reset options:

1. Open the user menu in the top-right application header.
2. Select **Reset demo state**.

Reset restores workflows, cases, organizations, users, teams, roles, permissions, tasks, approvals, documents, notifications, service state and audit seed data.

For manual reset, clear the `resolve.store.v3` localStorage key and reload the page.

## Demo walkthrough

1. Open the dashboard and review organization, case, identity, approval and document totals.
2. Use the tenant selector to switch the demo organization context.
3. Open Organization and create a new organization.
4. Open Users and provision a user, assign a role and change status.
5. Open Teams and add or remove a user from a team.
6. Open Roles & Permissions, edit a custom role or assign a role to a user.
7. Open Tasks and create or complete a task linked to a case.
8. Open Approvals and approve or reject a pending request.
9. Open Documents and upload a simulated document to a case.
10. Open Audit Log and verify the generated action history.
11. Use global search to find cases, workflows, users, teams, roles or tasks.
12. Reset the demo state from the user menu.

## Backend independence

No prototype flow calls a Resolve microservice or backend API.

The code does not use fetch, Axios, WebSocket, SSE, database SDKs or service credentials for application interactions.

Existing backend infrastructure in sibling folders remains outside the frontend and is not contacted by this prototype.

## Known limitations

- Authentication UI and real JWT/refresh/MFA integration are not implemented.
- Case statuses use the existing prototype status model rather than every canonical SRS lifecycle status.
- Case assignment history, close/reopen reasons and soft-archive behavior are partial.
- Workflow rules and workflow runtime instances are not implemented as full structured-rule services.
- Notification preferences and a backend notification inbox are not implemented.
- Document upload is simulated; it does not transfer a real file to S3.
- Audit entries are local mock records, not immutable server records.
- Pagination is not uniform across every list module.
- Browser automation was not available for a click-level visual walkthrough.

## Future backend integration

Backend integration should preserve this module structure and replace `resolve-store.tsx` mutations with typed API clients incrementally.

Recommended order:

1. Authentication/session and permission context
2. Organization and tenant APIs
3. User/team/RBAC APIs
4. Case/task/approval APIs
5. Document service APIs
6. Audit and notification APIs
7. Workflow-definition/runtime APIs

Internal service credentials and endpoints must remain outside browser code.
