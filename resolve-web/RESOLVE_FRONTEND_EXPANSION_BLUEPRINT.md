# Resolve Frontend Expansion Blueprint

## Document scope and evidence basis

This document defines how to expand the existing `resolve-web` frontend prototype without replacing or unnecessarily reimplementing it.

No application source files, routes, components, styles, or backend code were changed while producing this blueprint.

The primary documentation set reviewed is:

- `Resolve_Documentation/General/SRS.md`

- `Resolve_Documentation/Contracts/User_Team_Service.md`
- `Resolve_Documentation/Contracts/kafka.md`
- `Resolve_Documentation/kafka.md`

Service implementations and contracts were cross-checked for implementation reality:

- `resolve-authentication-service/`
- `Organization-Service/`
- `Resolve-User_Team_Service/`
- `resolve-rbac-service/`
- `Resolve_Document_Service/`

- `resolve-web/`

Where the SRS describes future functionality and a service implementation is absent, this blueprint labels the work as new or future prototype work. Documentation is not treated as implementation evidence.

# Section A — Existing frontend inventory

## A.1 Project and build system

`resolve-web` is a TanStack Start application using:

- React 19
- TanStack Start
- TanStack Router with file-based routing
- TanStack Query
- TypeScript
- Tailwind CSS 4
- Vite 8
- Nitro build runtime
- Radix UI primitives
- Recharts
- React Hook Form and Zod
- Lucide React
- Lovable TanStack configuration

Commands:

- `npm run dev` — development server
- `npm run build` — production build
- `npm run build:dev` — development-mode build
- `npm run preview` — preview build
- `npm run lint` — ESLint
- `npm run format` — Prettier formatting

The route tree is generated by TanStack tooling. `src/routeTree.gen.ts` must not be edited manually.

## A.2 Existing route structure

| Route | File | Purpose |
|---|---|---|
| `/` | `src/routes/index.tsx` | Operations dashboard |
| `/workflows` | `src/routes/workflows.index.tsx` | Workflow list and create/edit/delete dialogs |
| `/workflows/$id` | `src/routes/workflows.$id.tsx` | Workflow stage/node builder |
| `/cases` | `src/routes/cases.index.tsx` | Case list, filtering and create/edit/delete |
| `/cases/$id` | `src/routes/cases.$id.tsx` | Case detail, stage, comments, audit, documents and approvals |
| `/organization` | `src/routes/organization.tsx` | Users, teams and role-distribution overview |
| `/` and unmatched routes | `src/routes/__root.tsx` | Root layout, providers, metadata, 404 and error pages |

No login, logout, reset-password, MFA, audit console, notification inbox, RBAC administration, search, system-health, or dedicated profile route exists.

## A.3 Existing navigation and shell

`src/components/Shell.tsx` provides:

- fixed 240px frosted sidebar
- Resolve brand mark
- links for Dashboard, Workflows, Cases and Organization
- active-route indicator
- breadcrumb header
- page action slot
- notification bell with read-state dropdown
- active-workflow and awaiting-approval sidebar summary
- optional page drawer slot

## A.4 Existing dashboard

The dashboard shows:

- total cases
- open, in-review and blocked case counts
- resolved count
- active workflows
- pending approvals
- status breakdown
- priority breakdown
- recent audit activity
- recent cases

All values come from browser seed data and are not live backend metrics.

## A.5 Existing workflow module

The workflow prototype supports:

- workflow list
- create, rename and delete
- active, draft and archived status
- stage creation, edit and delete
- stage reorder
- task nodes
- approval-gate nodes
- nested task nodes
- workflow status control
- counts for stages/tasks/gates/running cases

This is a local hierarchy model, not a backend workflow-definition model. It does not include structured `IF/THEN` JSON rules, workflow instances, workflow-task execution logs or rule action payloads.

## A.6 Existing case module

The case prototype supports:

- case list
- search by reference, title or summary
- status, priority and workflow filters
- create, edit and delete
- title, summary, priority and owner fields
- case workflow stage conveyor
- previous/next stage
- task completion toggles
- approval-gate checklist state
- comments and nested comment rendering
- case activity timeline
- document table and simulated upload modal
- pending approval decisions

The prototype status model is lowercase `open`, `in_review`, `blocked`, `resolved`. The consolidated architecture uses the uppercase model `OPEN`, `ASSIGNED`, `INVESTIGATION`, `REVIEW`, `APPROVED`, `REJECTED`, `RESOLVED`, `REOPENED`.

No actual assignment history, case version/optimistic lock, close/reopen reason, bulk operation, task dependency, approval expiry or tenant isolation exists.

## A.7 Existing organization module

The organization route is read-only local seed UI that shows:

- role distribution cards
- users table
- team cards
- team member counts

It does not implement organization lifecycle management, organization detail pages, user CRUD, team CRUD, team membership management, role assignment or permission administration.

## A.8 Existing comments, audit, documents and approvals

### Comments

- top-level comments
- threaded rendering
- comment creation
- author/time/edit marker seed fields
- no edit, mention parsing or comment attachment UI

### Audit

- per-case local activity timeline
- actor, action, resource type, details and timestamp
- no raw audit query, tenant filters, pagination, sorting, immutable semantics or request/trace correlation

### Documents

- local filename, MIME type, size, uploader and scan status
- filename/KB simulated upload modal
- no actual file input, multipart upload, checksum, version history, signed download or virus-scan state transitions

### Approvals

- approval reason, requester, approver, status and decision notes
- approve/reject interactions
- no expiry, required role, dynamic routing, approval chain or delegation

## A.9 Notification and identity UI

The shell has a local unread notification dropdown for:

- case assigned
- approval requested
- case resolved
- mentions

There is no authentication UI or session provider. There is no role/permission-aware rendering. The notification dropdown is entirely local data.

## A.10 Reusable components

Key existing reusable modules:

- `Shell`, `Crumb`
- `NavItem` and `NotificationBell`
- `Modal`, `Field`, `TextInput`, `TextArea`, `Select`
- `PrimaryButton`, `DarkButton`, `GhostButton`, `DangerButton`
- `Tag`
- Radix UI wrappers in `src/components/ui`
- `rise`, `slidein` and `flowline` animation utilities
- `ResolveProvider` and `useResolve`
- `formatBytes`, `timeAgo`, `countNodes`, `statusLabel`

## A.11 State management and persistence

All data is held in `src/lib/resolve-store.tsx` and persisted to `localStorage` under `resolve.store.v2`.

The store contains:

- workflows and stages/nodes
- cases
- comments
- audit events
- documents
- notifications
- users
- teams
- approvals

It exposes local create/update/delete and toggle/approve/reject mutation methods. It is not an API cache and has no authentication, tenant context, optimistic locking or server error model.

## A.12 Design system

The existing visual system is a light frosted-console design:

- soft blue-gray background
- primary blue
- green success
- orange warning
- red danger
- white/transparent glass surfaces
- Inter and JetBrains Mono
- subtle glows
- restrained 12px rounded cards
- concise uppercase mono labels
- entrance rise animations

This design should be preserved for all expanded modules.

# Section B — Resolve product capability inventory

## B.1 Identity and organization domain

Services: Authentication, Organization, User & Team, RBAC.

Capabilities:

- organization provisioning and suspension
- organization slug resolution
- one organization per user
- JWT login with email/username and password
- access and refresh token handling
- logout and revocation
- password reset/change
- MFA/TOTP enrollment and verification
- tenant-scoped JWT context
- user provisioning and profile management
- teams and memberships
- system roles and custom tenant roles
- atomic permissions
- additive role/permission assignment
- effective permission lookup
- configurable token TTL at a should/could level

Implemented public service surfaces include organization, authentication, user/team and RBAC APIs. Password delivery, first-tenant RBAC bootstrap and notification delivery have known gaps.

## B.2 Case domain

The SRS defines:

- create and retrieve cases
- paginated/filterable/sortable tenant-scoped case lists
- update fields
- assign/reassign to user or team
- validated lifecycle state machine
- task and approval gates before transition
- status history
- optimistic locking/version conflict
- close/reopen with reason
- soft archive
- bulk operations
- human-readable timeline
- idempotent state-changing operations
- cross-tenant denial or 404

The canonical case statuses are:

`OPEN`, `ASSIGNED`, `INVESTIGATION`, `REVIEW`, `APPROVED`, `REJECTED`, `RESOLVED`, `REOPENED`.

## B.3 Task domain

- task create/update/complete
- task assignee user or team
- priority and due date
- pending/in-progress/completed/cancelled statuses
- task dependencies
- required-for-stage gating
- recurring/templated tasks as a could-have
- task SLA timers as a could-have

## B.4 Approval domain

- approval requested by a user
- specific approver or required role
- approve/reject decisions
- decision notes and timestamps
- expiry/re-request
- dynamic approver routing
- multi-step chains and delegation as could-have

## B.5 Collaboration domain

- case comments
- chronological listing
- threaded replies
- @mentions
- edit marker
- comment attachments as could-have

## B.6 Workflow domain

- declarative `IF/THEN` workflow definitions
- tenant-specific rule sets
- active/inactive definitions and versions
- actions: `REQUIRE_APPROVAL`, `CREATE_TASK`, `SEND_NOTIFICATION`
- workflow instances
- workflow-task execution records
- idempotent rule execution
- visual drag-and-drop workflow designer explicitly out of scope

The existing frontend visual conveyor/builder should not be represented as a tenant rule designer until a backend contract exists.

## B.7 Document domain

- upload metadata and S3-compatible object storage
- case or comment attachment
- MIME/size validation
- SHA-256 checksum
- virus scan state
- clean-gated downloads
- document versions
- pre-signed downloads
- OCR extraction and search indexing as advanced features

The Document Service currently implements upload/list/detail/download/version behavior and a transactional outbox.

## B.8 Audit and observability domain

- append-only significant action log
- actor, tenant, action, resource, old/new values
- request and trace correlation
- immutable audit API
- per-case human-readable timeline
- event-driven eventual consistency
- audit filters/pagination/sorting/export could-have
- health, readiness, metrics and distributed tracing

## B.9 Notification domain

- assignment notifications
- approval-request notifications
- case resolution/rejection notifications
- @mention notifications
- in-app and email channel preferences
- notification read status
- notification inbox

Task 10 defines a read API, and a notification entity is part of the canonical schema, but no implemented notification service exists in this repository.

## B.10 Search domain

- PostgreSQL baseline case search
- filter and paginate by tenant
- optional search over comments/document metadata
- advanced dedicated search indexing for later phases
- no full faceted/analytics UI in the initial release

## B.11 Event and reliability domain

- ten domain topics
- transactional outbox
- partition/ordering by aggregate ID
- at-least-once delivery
- duplicate/redelivery protection
- retry and DLQ behavior
- per-service consumer groups
- Kafka must not block core business writes

The frontend should represent this in operational status and eventual-consistency UI, not as a general event-management dashboard unless a backend API is added.

# Section D — Proposed navigation

Preserve the existing sidebar style and shell. Use a grouped but compact hierarchy:

```text
Resolve
├── Workspace
│   ├── Dashboard
│   ├── Cases
│   ├── Tasks
│   └── Approvals
├── Operations
│   ├── Workflows
│   ├── Workflow Rules
│   └── Documents
├── Administration
│   ├── Organization
│   ├── Users
│   ├── Teams
│   ├── Roles & Permissions
│   └── Authentication Settings
├── Governance
│   ├── Audit
│   ├── Notifications
│   └── System Health
└── Account
    ├── Profile
    └── Security & MFA
```

Navigation rules:

- Do not add separate duplicate “Case Approvals” and “Case Tasks” when these belong naturally on the case detail page.
- `Tasks` can be a cross-case task inbox, but it depends on a Case/Workflow backend and therefore remains future/prototype until APIs exist.
- `Approvals` can be a cross-case queue, also future until backend support exists.
- Keep `Organization` as the tenant overview and move detailed user/team/RBAC pages beneath it or beside it logically, not as redundant dashboard cards.
- Add only routes that are backend-supported or explicitly marked prototype in the UI.
- Hide features based on effective permissions, while still handling 403 responses from the backend.

- authentication in session state only
- documents and document versions in Document mock data
- audit events in Audit mock data
- cases/tasks/approvals/workflow data only once service contracts exist

# Section H — Prototype interaction plan

## H.1 Create

- generate stable client UUIDs/ids for prototype records
- validate required fields before adding records
- create one entity and append audit/activity entries
- use idempotency-key-like prototype submit state to prevent duplicate UI submissions
- for organizations, users, teams, documents and future service writes, keep the submitted key stable across a retry
- show success toast or inline confirmation and navigate to detail when appropriate

## H.2 Read

- support list/detail navigation
- seed empty states separately from loading states
- implement paginated response shape with `content`, `page`, `size`, `totalElements`, `totalPages`
- show cross-tenant/not-found neutral states
- keep read models service-scoped instead of creating global joined tables

## H.3 Update

- prefill edit forms from selected entities
- preserve immutable fields

# Implementation guardrails

- Preserve existing route names and the frosted-console design.
- Add backend adapters incrementally; do not replace the working local store for every domain at once.
- Keep the existing prototype label visible until real APIs exist.
- Do not add direct browser calls to internal or credential endpoints.
- Do not embed permissions in JWT assumptions; effective permissions come from RBAC.
- Do not expose private keys, secrets or MFA provisioning secrets.
- Do not implement the visual state-machine designer or advanced search UI without backend support.
- Do not add hard-coded role-only checks instead of permission checks.
- Do not silently convert mock interactions into claims of real integration.

# Concise architectural summary

The existing frontend is a strong visual prototype for dashboard, workflows, cases, comments, documents, approvals and organization display. It is not yet an implementation of the latest Resolve architecture because it has no authentication UI, no real service data, no RBAC administration, no canonical case/task/approval backend model and no audit/search/workflow-rule services.

The largest gaps are:

1. authentication and permission-aware session behavior
2. organization, user, team and role administration
3. canonical case/task/assignment/status model
4. real document upload/version/scan behavior
5. immutable audit console and notification inbox
6. structured workflow rules and workflow instances

The recommended sequence is identity foundation, organization/RBAC, case/task/approval domain, document/audit/notification domain, and workflow-rule/dashboard completion.
